# ADR-003 — Position UPSERT & Deduplication

**Date:** 2026-02-24 | **Status:** Accepted | **Version:** V0.5-Pre

## Problem

`active_positions` accumulated multiple rows per ticker because `open_position()` used a plain `INSERT`. The Guardian Exit Matrix evaluated each row independently, causing multiple SELL orders to fire on the same position — a financial correctness defect.

## Decision

**Database-level UNIQUE index + UPSERT** (over application-level check-before-insert).

- Added `UNIQUE INDEX` on `active_positions.ticker`
- Converted `open_position()` to `INSERT ... ON CONFLICT (ticker) DO UPDATE`

## Why Not Application-Level Guard?

Application-level `SELECT → INSERT/UPDATE` is two separate round-trips with no transaction wrapping. A concurrent call (e.g., `sync_reality()` running in the same cycle window) could insert a duplicate between the SELECT and INSERT. The `ON CONFLICT` clause is a single atomic operation.

## Dual Conflict Behaviour

| Call type | `timestamp` param | Conflict resolution |
|-----------|------------------|---------------------|
| New BUY | `None` | `DO UPDATE` — accumulates qty, recalculates weighted-avg entry price |
| Sync-restore | Supplied | `DO NOTHING` — real positions never overwritten by ghost restore |

## Startup Migration

`_initialize_db()` runs an idempotent migration on every boot that consolidates any pre-existing duplicates. Self-healing — no manual SQL step needed.

## Consequences

✅ Exactly one row per ticker guaranteed at all times  
✅ Guardian fires at most one SELL per ticker per cycle  
✅ `open_position()` safe to call multiple times per cycle  
⚠️ `timestamp` parameter is now overloaded as a conflict-resolution signal — callers must understand the contract
