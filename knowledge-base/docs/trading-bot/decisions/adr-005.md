# ADR-005 — 5-Minute Guardian Split Loop

**Date:** 2026-02-25 | **Status:** Accepted | **Version:** V0.5.2-Pre

## Problem

In V0.5.1, Guardian ran inline inside `run_cycle()` at the start of each 30-minute cycle. A position crossing a stop immediately after a cycle completed could wait **up to 28 minutes** before being acted on — accumulating unnecessary losses or missing profit-taking windows.

## Decision

**Extract Guardian into `run_guardian_pass()` and run it every 5 minutes between full cycles.**

```
minute % 30 < 1  →  run_cycle()          Full cycle (sync + Guardian + Sentinel + Brain)
otherwise        →  run_guardian_pass()   Exit-only pass, every 5 min
```

## Why 5 Minutes?

- Divides 30 cleanly — no scheduling drift with full-cycle boundaries
- 6× more frequent than 30-minute cadence
- Guardian-only pass is cheap: ~6s (Gemini) for a typical 5-position portfolio

## Scheduling

```
:00, :30  →  full run_cycle()
:05, :10, :15, :20, :25  →  Guardian-only
:35, :40, :45, :50, :55  →  Guardian-only
```

No overlap possible — 5 divides 30 exactly.

## Why Not Threading?

`DBManager` uses synchronous `psycopg2` — not safe for concurrent access. The sequential 5-minute split achieves the latency goal without introducing race conditions.

## Consequences

✅ Maximum exit latency: 28 min → 5 min  
✅ `run_guardian_pass()` reused by `run_cycle()` — no logic duplication  
⚠️ `wait_for_next_window()` removed — update external scripts to `wait_for_next_guardian_check()`  
⚠️ No separate alerting if `run_guardian_pass()` raises — logged, retried next 5-min boundary
